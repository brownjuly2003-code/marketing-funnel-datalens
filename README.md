# Рекламная воронка и атрибуция по каналам

Локальный учебный расчёт сравнивает три модели атрибуции синтетических подписок и сохраняет суммы в копейках. Его проверяют три независимых пересчёта: SQL в SQLite заново считает веса каналов и воронку; скрипт `scripts/audit.py` по этим весам проверяет копейки каждой подписки и канальные итоги, включая CPA и маржу; SQL на сервере ClickHouse сам строит из исходных событий и расходов распределение, CPA и маржу.

**Статус — в работе.** Все данные синтетические. Для подключения DataLens подготовлены таблицы ClickHouse с долями каналов в подписках, расходами, CPA и маржой.

## Задача и схема

Офлайн-расчёт использует стандартную библиотеку Python 3.11+ и SQLite. Отдельный загрузчик отправляет исходные события и расходы на сервер ClickHouse, где SQL заново рассчитывает атрибуцию и канальные показатели.

## Запуск

Команды даны для bash и выполняются из корня репозитория. В PowerShell вместо префикса `PYTHONPATH=src` один раз задайте `$env:PYTHONPATH = 'src'`. Генерация и аудит:

```bash
PYTHONPATH=src python -m marketing_funnel --out reports/demo --size 120 --seed 20261031
python scripts/audit.py reports/demo
```

Проверки (pytest 9.1.1 и Ruff 0.15.22 закреплены в `pyproject.toml`, группа `dev`) запускаются в CI с Python 3.11 по [ci.yml](.github/workflows/ci.yml); интеграционные тесты поднимают сервер ClickHouse в контейнере:

```bash
python -m pip install '.[dev]'
python -m ruff check .
python -m ruff format --check .
python -m pytest -q
python -m pytest -q -s tests/clickhouse_cases.py
```

Доказательством служат полные прогоны CI на iMac: [витрина в ClickHouse](docs/runs/2026-11-18-clickhouse.md), [заказы AgentFlow](docs/runs/2026-11-18-agentflow.md), [правки после аудита 19.11](docs/runs/2026-11-19-second-audit.md) — последний полный прогон `marketing-funnel-datalens_20261119-161024`: 44 модульных и 6 интеграционных тестов прошли.

Выходная папка должна быть новой: существующие результаты не перезаписываются. Для повторного прогона выберите другое имя. Повтор расчёта сохранённого входа: `python -m marketing_funnel --input docs/runs/2026-10-31-synthetic/inputs.json --out reports/replay`. CLI создаёт inputs.json, report.json и manifest.json с SHA-256; seed применён только при генерации.

## Витрина в ClickHouse

Для нового снимка укажите свободное имя базы. В примере `p16-clickhouse` — имя запущенного Linux-контейнера ClickHouse 24.8.14.39. Команды выполняются из корня репозитория. С настроенным локальным `clickhouse-client` опустите `--container` в команде загрузки и выполните запрос этим клиентом.

```bash
PYTHONPATH=src python scripts/load_clickhouse.py --input docs/runs/2026-10-31-synthetic/inputs.json --database marketing_jan --container p16-clickhouse
docker exec p16-clickhouse clickhouse-client --query "SELECT channel, conversions, cpa_cents, margin_cents FROM marketing_jan.channel_metrics WHERE model = 'last_click' ORDER BY channel"
```

Загрузчик проверяет вход, строит таблицы в отдельной базе и переименовывает её после расчёта. Если имя занято, повтор завершается ошибкой, и предыдущий снимок остаётся доступным.

| Таблица | Что содержит |
|---|---|
| `events`, `spend` | События с временем UTC и расходы по каналу за весь снимок |
| `attribution` | Время подписки, модель, канал, вес и распределённые копейки |
| `channel_metrics` | Одна строка на модель и канал. При нуле подписок CPA равен `NULL` |
| `user_funnel` | Пять шагов воронки по порядку и число уникальных пользователей, достигших каждого шага |

По `converted_at` можно отобрать подписки в `attribution` после расчёта весов. Расходы в исходном снимке заданы за весь период, поэтому дневной CPA по этому набору рассчитать нельзя. [SQL атрибуции](sql/clickhouse/attribution.sql) · [SQL витрины](sql/clickhouse/channel_metrics.sql)

## Стенд DataLens

Стенд подготовлен, но ни разу не запускался. Файлы написаны по документации и исходному коду DataLens OSS v2.9.0; работает ли стенд, покажет первый прогон. [Протокол подготовки и источники](docs/runs/2026-11-19-stand-prep.md)

Запуск на Linux-машине с Docker (compose v2) и Python 3.11+, в том числе в GitHub Codespaces по [.devcontainer/devcontainer.json](.devcontainer/devcontainer.json), из корня репозитория:

```bash
bash stand/run.sh
```

Скрипт без участия человека:

1. записывает ресурсы машины и останавливается, если под Docker меньше 10 ГБ свободного диска;
2. поднимает [stand/docker-compose.yml](stand/docker-compose.yml): DataLens v2.9.0 без авторизации, temporal и демо-данных, плюс ClickHouse 24.8.14.39;
3. генерирует снимок с seed 20261031, сверяет `inputs.json` и `report.json` с SHA-256 эталона из [manifest.json](docs/runs/2026-10-31-synthetic/manifest.json) и загружает витрины существующим загрузчиком;
4. через API DataLens создаёт подключение, датасеты `channel_metrics` и `user_funnel`, четыре карточки и дашборд с селектором модели;
5. читает числа из DataLens для каждой модели и сравнивает их с [report.json](docs/runs/2026-10-31-synthetic/report.json);
6. делает снимки страниц, `docker stats`, `docker compose logs`;
7. в конце выполняет `docker compose down -v`.

Результат — `stand/out/`: `SUMMARY.txt`, `comparison.txt`, `numbers.json`, ответы API в `api/`, снимки в `screenshots/`, логи.

Успех — код выхода 0. Так задумано, но ни разу не проверено прогоном. Код 0 означает три вещи:

- числа всех 15 строк каналов, доли без атрибуции и пяти шагов воронки совпали с эталоном;
- каждая карточка через `/api/run` вернула HTTP 200 и непустой список строк таблицы `data.rows` (форма ответа взята из исходного кода DataLens и не проверена);
- каждая страница для снимков ответила HTTP-статусом ниже 400; у дашборда скрипт дополнительно ждёт класс готовности `dash-body-loaded`, содержимое остальных страниц не проверяется.

С `SKIP_SCREENSHOTS=1` код 0 покрывает только первые два пункта. Какой из двух успехов получен, пишет строка `overall:` в `SUMMARY.txt`.

При расхождении скрипт выводит таблицу «ожидалось / получено» и завершается с кодом 1. Остальные коды описаны в шапке [stand/run.sh](stand/run.sh).

## Ограничения и следующий этап

Для проверки в DataLens предстоит подключить `channel_metrics` и сравнить маркетинговые карточки с эталоном при выборе модели и канала. Для этого подготовлен [стенд](#стенд-datalens); он ещё не запускался. Для заказов AgentFlow подготовлен отдельный SQL-датасет с полями `branch`, `order_day` и `orders`. Осталось проверить подключение к работающему источнику и оба селектора в интерфейсе. [Настройки датасета и карточки заказов](docs/DASHBOARD.md#заказы-agentflow-по-филиалу-и-периоду)

Ограничения:

- DataLens не запускался: подключение витрины `channel_metrics`, датасеты, карточки и селекторы модели атрибуции, канала, филиала и периода не проверены.
- Стенд DataLens написан по документации и исходному коду релиза и не запускался. Пути API, тела запросов, конфигурации карточек и ожидания на страницах подтвердит только первый прогон `stand/run.sh`. Селектор модели в сверке чисел заменён фильтром в запросе к API; клик по селектору скрипт не делает. Список мест, где поломка вероятнее всего, — в [протоколе подготовки](docs/runs/2026-11-19-stand-prep.md#что-написано-вслепую-и-скорее-всего-сломается).
- Живой ClickHouse AgentFlow не подключался: дневной SQL заказов проверен на контрольных данных в таблице с подлинной схемой AgentFlow (коммит `250623a`), кластер AgentFlow был недоступен.
- Часовой пояс дня заказа — допущение. `toDate(order_date)` по `DateTime64(3)` без явного пояса берёт пояс сервера ClickHouse. В тесте пояс не задавался; в прогоне 18.11 он не записывался, с 19.11 тест печатает `SELECT timezone()`, и тестовый контейнер ответил `UTC` ([протокол](docs/runs/2026-11-19-second-audit.md)). Результат теста от пояса не зависит. На сервере AgentFlow пояс нужно проверить до сверки карточки. [Подробнее](docs/DASHBOARD.md#заказы-agentflow-по-филиалу-и-периоду)
- В time decay квоты копеек считаются в числах с плавающей точкой, точное целочисленное правило действует только для linear и last click. Если остатки в time decay математически равны, округление может отдать лишнюю копейку не первому по имени каналу. Пример: пять кликов канала a и один клик b в один момент, подписка на 9 копеек — time decay даёт a 7 и b 2 копейки вместо 8 и 1. Сумма по подписке при этом сохраняется, а аудит и ClickHouse применяют то же правило с плавающей точкой и такую ошибку не поймают.
- Все данные синтетические; атрибуция описательная и не оценивает причинный эффект рекламы.
